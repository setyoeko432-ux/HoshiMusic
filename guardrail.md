1. Mission
Maintain Hoshi Music as a stable, private, local-first Android music player. Prefer the smallest verifiable change over broad modernization. A successful task preserves existing behavior outside the requested scope and reports actual evidence.

3. Absolute prohibitions
Without explicit user approval, never:

Upgrade or downgrade JDK, Gradle, AGP, Kotlin, SDK, NDK, CMake, plugins, or dependencies.
Add org.gradle.toolchains.foojay-resolver-convention or another automatic JDK resolver.
Install or auto-download a JDK, SDK, NDK, CMake, plugin, or new dependency.
Change the project to Java 21 or Java 25 to solve a build error.
Add android.permission.INTERNET, network APIs, cloud services, accounts, ads, analytics, telemetry, or online crash reporting.
Add, generate, expose, commit, or print keystores, passwords, tokens, API keys, service-account files, or machine credentials.
Use fallbackToDestructiveMigration() as a shortcut for a missing Room migration.
Delete or reset user data, playlists, favorites, queues, statistics, metadata, or settings.
Run destructive Git commands such as git reset --hard, git clean -fd, force push, history rewrite, or mass deletion.
Claim that a build, test, lint check, feature, codec, route, or audio property works without evidence.
Normal resolution of already declared and pinned dependencies from google() or mavenCentral(), and the pinned Gradle 8.9 distribution, is allowed only when the user intentionally starts Sync/Build. This does not authorize adding or upgrading anything.

Set or retain:

org.gradle.java.installations.auto-download=false

5. Stop-and-ask conditions
Stop immediately and report the exact blocker when:

JDK 17 is not installed or Gradle is running on another JVM.
A required SDK, NDK, CMake version, plugin, or dependency is unavailable.
A change would require installing, downloading, or upgrading a component.
A Room migration cannot be reconstructed safely.
The requested edit crosses into an unrelated subsystem.
A command would delete files, data, caches outside the project, or Git history.
The first compile/test error is not understood.
A proposed fix changes product behavior rather than correcting the requested defect.
Do not “solve” a stop condition by improvising a new plugin, dependency, version, architecture, or fallback.

6. Build-system protocol
Before changing any of these files, explain the intended edit and request approval:

settings.gradle.kts
root or module build.gradle.kts
gradle.properties
gradle-wrapper.properties
version catalogs
ProGuard/R8 configuration
CMake/NDK configuration
For build diagnosis:

Inspect the existing files; do not rewrite them from a generic template.
Verify the Gradle JVM first with gradlew.bat --version on Windows or ./gradlew --version elsewhere.
If the JVM is not Java 17, stop. Ask the user to select a locally installed JDK 17 in Android Studio.
Do not add Foojay or upgrade Gradle to accommodate the wrong JVM.
Run the narrowest task first: :app:compileDebugKotlin --stacktrace.
Fix the first root-cause error before running broader tasks.
Never use dependency/version upgrades as an automatic error-recovery strategy.
Do not hard-code a machine-specific JDK path in project files. A temporary shell JAVA_HOME or an IDE-local Gradle JDK setting may be used after the user supplies or confirms the path.

7. Change protocol
For every task:

Restate the exact scope and protected areas.
Inspect all relevant call sites before editing.
Present a short plan.
Identify files that will be modified.
Request approval for build-system, database, permission, dependency, or architecture changes.
Make the smallest coherent patch.
Do not combine cleanup, modernization, and feature work unless explicitly requested.
Re-read the changed code and inspect the diff.
Run focused validation.
Stop after the requested phase and report results.
Do not remove code merely because text search finds one reference. First rule out Android callbacks, manifest registration, Compose calls, Room-generated code, WorkManager reflection, JNI bindings, serialization, ProGuard rules, and tests.

8. Dependency and plugin rules
Prefer existing dependencies and platform APIs.
A new dependency or plugin requires explicit approval before editing files or downloading it.
State its purpose, version, size/complexity cost, license, privacy impact, and simpler alternatives.
Do not add a resolver merely because a local tool is missing.
Do not remove a dependency until all imports, generated code, reflection, serialization, tests, and ProGuard consumers have been checked.
Keep repositories limited to the existing approved sources unless the user explicitly approves another repository.
9. Privacy and data safety
Hoshi Music is local-first:

Audio and user data must remain on-device unless the user explicitly exports them.
Do not transmit filenames, metadata, lyrics, listening history, device names, or diagnostics.
Request only permissions required by the active feature.
Denial of an optional permission must not block core local playback.
Preserve user data across updates with explicit Room migrations.
Do not silently enable cloud backup or external synchronization.
10. Audio correctness
Do not claim bit-perfect, Hi-Res, active codec, active route, USB-exclusive, or lossless processing from heuristics alone.
Distinguish device capability from the route/format actually used for playback.
DSP bypass must not be described as bit-perfect unless the entire output path is verified.
Unknown information must remain unknown; do not replace it with plausible defaults.
Audio/DSP changes require focused tests and real-device verification notes.
11. Validation ladder
Use the smallest applicable sequence:

Static inspection and diff review.
:app:compileDebugKotlin --stacktrace
:app:testDebugUnitTest
:app:lintDebug
:app:assembleDebug
:app:assembleRelease only when requested and signing requirements are understood.
Real-device testing for permissions, playback service, Bluetooth, USB, storage, and audio behavior.
If a step fails, stop at the first root cause. Do not hide it behind subsequent errors or version changes.

12. Truthfulness requirements
Always distinguish:

inspected vs assumed;
compiled vs not compiled;
unit-tested vs device-tested;
available device vs active route;
romanization vs translation;
source code present vs feature actually wired;
warning vs confirmed bug.
Never fabricate command output, test results, file contents, API behavior, migration history, or successful downloads.
